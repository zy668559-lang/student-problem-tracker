# DECISIONS

## 2026-03-18

### D1 已按 staging draft -> review -> materialize 闭环落成
- 决策：本轮以 `review_drafts` 为 staging draft 真相源，上传只写草稿，审核通过后再 materialize 到正式学生档案。
- 原因：这样既能把“自动搬运”和“正式写库”拆开，又不需要为本轮引入 worker / cron 或大规模底层重构。

### 审核对象正式切换为 draft，而不是 diagnosis
- 决策：`/review-queue`、`/review-draft/[id]`、`/api/review/[id]` 都围绕 draft id 工作，正式 diagnosis 只在审批通过后生成。
- 原因：如果继续直接审核正式 diagnosis，本轮最关键的“先草稿、后入库”边界就站不住。

### D1 e2e 必须显式恢复 parent 的 active student 上下文
- 决策：管理员审核后返回家长视角时，测试里显式恢复 `activeStudentId`，不依赖默认学生。
- 原因：D1 审批流会切到管理员会话；如果回父账号后吃默认学生，容易把多学生隔离问题误判成产品 bug，也会让 Heartbeat / 跟进 / 时间轴用例出现假失败。

### 试用次数在创建 draft 时就消耗
- 决策：D1 保持“创建 staging draft 即计入一次上传使用量”，正式 materialize 时不再重复增加试用计数。
- 原因：从产品语义上，自动抓取与草稿生成已经消耗系统资源；如果等正式入库才计数，会把真实使用量和审核状态混在一起。

### D1 本轮边界继续保持严格
- 决策：不做正式支付 / 订阅，不做 worker / cron，不做 Heartbeat Lite，不做新的前台大改，不做全自动直写正式库。
- 原因：D1 的唯一目标就是把“草稿进队列 -> 审核 -> 正式入库”的系统底座站住。

## 2026-03-17

### 为什么当前先做 U1.2
- 决策：当前先做 `U1.2 前台文案口语化真收口`，不切新功能轮。
- 原因：`U1` 和 `U1.1` 已把结构和视觉收住，但真实页面验收时，家长页、孩子页、会员页仍残留后台味、技术字段味和术语味，家长读起来还不够像陈老师在说话。

### U1.2 只收前台文案，不动逻辑底座
- 决策：本轮只改家长总览页、孩子首页、会员页、相关 CTA 与它们依赖的前台文案来源，不新增业务逻辑，不改后端契约，不碰多学生隔离底座。
- 原因：这轮要解决的是“说得不够人话”，不是“能力不够”。

### U1.2 的文案原则
- 决策：本轮前台文案统一遵守以下原则：
  1. 先结论，后解释
  2. 用短句，不写报告腔
  3. 用家长听得懂的话，不用系统术语
  4. 家长页强调“现在卡哪、为什么还要继续跟”
  5. 孩子页强调“今天先做什么、下次回来看什么”
  6. 会员页强调“差异、边界、升级理由”
- 原因：目标是把前台页面从“已经像产品”推进到“真能拿给家长看”。
